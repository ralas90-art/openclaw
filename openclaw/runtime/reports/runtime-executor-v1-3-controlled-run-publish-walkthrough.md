**Version:** 1.3

**Status:** ✅ Production Ready

## Summary

Runtime Executor v1.3 adds `/run_publish <bot_slug> <user_request>` — a single admin-only Telegram command that atomically:

1. Executes an approved runtime bot
2. Captures the **exact generated filename** from that execution
3. Immediately publishes only that specific file to Google Drive

This eliminates the two-step manual flow (`/run_bot` → `/drive_publish_pending`) for controlled, immediate publishing while leaving all existing commands unchanged.

## Architecture: Exact-File Publishing

`/run_publish` publishes **only the file generated by the current command execution**, never an older pending file, never the "latest" file in the directory.

```
/run_publish content-forge <request>
      │
      ▼
  isChatAuthorized()  ← admin gate first
      │
      ▼
  runtimeExecutor.runBot()  ← executes bot
      │
      ▼
  result.filename  ← exact filename captured from THIS execution
      │
      ▼
  path.resolve(responsesDir, basename(filename))  ← scoped to telegram-responses/
      │
      ▼
  drivePublisher.publishExactRuntimeFile()  ← safe wrapper
      ├─ suffix check (_runtime_result.md)
      ├─ path scope check (must be in telegram-responses/)
      ├─ duplicate detection (checkAlreadyPublished)
      └─ publishFileToDrive() → Drive sync manifest created
```

---

## Safety Behavior

| Boundary | Enforcement Layer |
|---|---|
| Admin-only | `isChatAuthorized()` checked before any execution |
| Approved bots only | `runtimeExecutor.runBot()` enforces allowlist |
| Exact file — no directory scan | `result.filename` captured from executor, not from a directory scan |
| Path scope locked | `publishExactRuntimeFile()` resolves and validates path is inside `openclaw/outbox/telegram-responses/` |
| Filename suffix enforced | `publishExactRuntimeFile()` rejects files not ending in `_runtime_result.md` |
| No arbitrary paths | `path.basename()` + controlled join — no user-provided path accepted |
| No secret exposure | Error messages never include stack traces, env values, API keys, or tokens |
| Duplicate detection | `checkAlreadyPublished()` returns existing link if already published |
| Drive failure fallback | Returns filename + `/drive_publish_pending` recommendation |
| `/run_bot` unchanged | Manual flow untouched — no auto-publish added |

## publishExactRuntimeFile() — Safe Library Wrapper

`publishExactRuntimeFile(exactFilePath, options)` was created in `drive-publisher.js` as a purpose-built wrapper that enforces all safety invariants at the **library level** — independently of the handler. This makes the safety boundaries testable in isolation and ensures any future handlers that want to publish a runtime file go through a single enforced path.

**Confirmed:** `publishFileToDrive()` already existed. `publishExactRuntimeFile()` wraps it with additional safety:
1. Filename suffix guard (`_runtime_result.md`)
2. Path scope guard (`openclaw/outbox/telegram-responses/`)
3. Duplicate detection via `checkAlreadyPublished()`
4. Delegates to `publishFileToDrive()` for Drive API / local sync + manifest creation

---

## Duplicate Detection Behavior

When `/run_publish` is called for a file that was already published:

1. `publishExactRuntimeFile()` calls `checkAlreadyPublished(resolvedPath)`
2. Scans all `publish_manifest_*.json` files in `google-drive-sync/`
3. Finds a match with `status: 'published'`
4. Returns `{ status: 'already_published', drive_web_url: '...', ... }`
5. Handler returns:

```
⚠️ Already Published — No Duplicate Upload

🤖 Bot: Content Forge
📄 File: `2026-06-04_..._runtime_result.md`
🔗 Existing Drive Link: https://drive.google.com/...

Next command: /drive_latest
```

---

## Drive Failure Fallback Behavior

When Drive publishing fails (misconfigured local root, API error, etc.):

```
✅ Bot execution successful!
🤖 Bot: Content Forge
📄 File: `2026-06-04_..._runtime_result.md`

⚠️ Drive Publish Failed: GOOGLE_DRIVE_LOCAL_ROOT is not configured.
To publish manually, run: /drive_publish_pending
```

The generated filename is always returned so the operator can manually publish it.

## Recommendation for v1.4

**v1.4 Suggestion: `/run_schedule` — Queued Controlled Publishing**

Allow scheduling a bot execution + publish for a future time or repeating cadence:

```
/run_schedule content-forge daily 09:00 Create TikTok hooks for Cresca OS
```

This would:
- Queue the request for a specific time
- Execute `/run_publish` atomically at the scheduled time
- Post the result to Telegram when complete
- Support repeating schedules (daily, weekly)

Prerequisites before v1.4:
- Persistent queue store (Supabase table or Railway cron)
- Telegram async notification channel
- Rate limiting per chat ID
