# GHL Sync Phase 1.5 - Operational Hardening

This phase transforms the Cresca OS GHL integration into a production-safe operational infrastructure layer.

## Architecture Overview

Cresca OS uses a multi-layered approach to ensure reliability and tenant isolation:

1. **Queue Abstraction**: Decouples sync requests from execution. Supports retries and dead-letter routing.
2. **Idempotency Layer**: Prevents duplicate CRM operations using a unique key (`tenant:entity:id:event`).
3. **Provider Abstraction**: Standardizes CRM operations (Contacts, Opportunities, etc.) across different platforms (starting with GHL).
4. **Policy Engine**: Enforces tenant-specific sync rules before execution.

## Key Features

### 1. Idempotency Protection
A dedicated `sync_idempotency` table tracks every sync attempt. Successful or in-progress syncs are automatically blocked from re-processing unless explicitly forced.

### 2. Formal State Machine
Sync events follow a strict lifecycle:
`queued` → `processing` → `completed` | `failed` | `retrying` → `dead_lettered`.

### 3. Safe Tag Namespacing
All tags generated by Cresca OS are prefixed with `cresca:` (e.g., `cresca:priority_high`) to prevent accidental triggers of client-defined GHL workflows.

### 4. Dead Letter Handling
Unrecoverable failures are moved to the `dead_letter_events` table for manual review and replay. This triggers a high-severity alert.

## Observability

Operational health is tracked in the `sync_metrics` table:
- **Sync Success Rate**: Percentage of `completed` vs `failed`.
- **Provider Latency**: Response time of external CRM APIs.
- **Idempotency Hits**: Number of prevented duplicates.
- **Queue Depth**: Number of pending jobs.

## Security Hardening

- **Credential Masking**: Secrets are redacted in all logs and audit trails.
- **Audit Logging**: Every sync operation is recorded in the `audit_logs` table with user/system attribution.
- **Payload Redaction**: Sensitive fields (tokens, passwords) are automatically removed from event payloads before storage.

## Testing

Validate the hardened flow using:

```bash
node scripts/test-ghl-sync.js --tenant-id=TENANT_ID --lead-id=LEAD_ID
```

This script will attempt multiple syncs to demonstrate idempotency blocking and proper state transitions.
